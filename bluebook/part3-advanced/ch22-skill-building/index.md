# 第 22 章 打造 Skill：把知识蒸馏为可执行能力

你读过一篇好文、看过一门好课、跑顺一个流程——这些「隐性知识」最该被固化成 **Skill**，下次一句话调用。

## Skill 长什么样

一个 Skill 是一个目录，核心是 `SKILL.md`：

```markdown
---
name: weekly-report
description: 生成结构化周报。当用户要「写周报/周报模板/本周总结」时使用。
---
# Weekly Report Skill
## 步骤
1. 向用户要本周完成项、进行中、风险三类。
2. 按固定模板输出（成果/进行中/下周计划/阻塞）。
3. 默认控制在 300 字内。
## 模板
**成果**：...
**进行中**：...
```

`name` 是标识，`description` 是「何时该用」的触发说明——写清楚触发词，WorkBuddy 才会自动匹配。

## 怎么造一个

1. 选一个你**反复做、步骤固定**的事（周报、封面、数据看板）。
2. 把成功那次的提示词和校验点提炼成 `SKILL.md`。
3. 放到技能目录：
   - **用户级**（所有项目）：`~/.workbuddy/skills/`
   - **项目级**（仅本项目）：`<项目>/.workbuddy/skills/`
4. 下次直接说「用 weekly-report 这个技能写周报」。

## 好的 Skill 长这样

- **触发清晰**：description 写清「用户说什么时用我」。
- **步骤具体**：不写「好好写」，写「先要 ABC，再按模板输出」。
- **有验收**：内置自检清单，产出不对会重来。
- **边界明确**：什么不该做、要确认什么。

::: tip 从书/视频蒸馏
读一本方法论书或看一门课，问自己：「哪一步能变成可执行的指令？」把那一步写成 Skill 的一个环节，比整本搬运有用。
:::

::: info 用户级 vs 项目级
通用的（周报、封面）放用户级，处处可用；业务特有的（你们内部系统操作）放项目级，随仓库走、不泄露。
:::

::: warning 别过度 Skill 化
一次性、低频、每次都不同的事，直接对话更省事。Skill 留给「高频 + 固定」的流程。
:::
